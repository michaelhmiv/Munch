# Munch MCP ↔ Website Parity Audit

**Audit date:** 2026-08-21

## Executive summary

The original parity program is implemented and deployed. The capability registry now assigns all 72 registered MCP tools to 60 outcome contracts. Of those contracts, 53 are complete on both MCP and the website; the remaining 7 are explicitly website-only product workflows, not unresolved gaps. There are no `partial` contracts, no non-null `gap` fields, and no outstanding target PRs in the manifest.

The final implementation slice, atomic website recipe composition (`mealPlan.compose`), merged as [PR #96](https://github.com/michaelhmiv/Munch/pull/96) at [`aa02e174`](https://github.com/michaelhmiv/Munch/commit/aa02e174f8e2d844cb18eca83a4eef684a089ff8). ## Intentional channel exceptions

These are product-boundary decisions recorded in the manifest. They are not parity failures.

| Contract                | Website behavior                                                | MCP behavior                                             | Decision                                                              |
| ----------------------- | --------------------------------------------------------------- | -------------------------------------------------------- | --------------------------------------------------------------------- |
| `meal.copy`             | Structured diary duplication via `POST /api/app/meals/:id/copy` | No dedicated copy tool; re-log through normal meal tools | Direct website diary convenience; no MCP gap                          |
| `grocery.manage`        | Edit/delete list items                                          | MCP exposes explicit additions and purchase state        | Website list-management control; no MCP gap                           |

| `billing.portal`        | Stripe subscription portal                                      | Not advertised through MCP                               | Subscription management is website-only                               |

| `household.manage`      | Household administration                                        | MCP consumes shared planning data only                   | Website-centric administration boundary                               |
| `account.export`        | Complete-account export from account portal                     | MCP exposes focused meal export separately               | Separate product scopes; no MCP gap                                   |

## What changed and why

The initial gaps were workflow gaps rather than missing database primitives: the website had canonical endpoints or services for several domains but lacked the user-facing route, editor, history control, or confirmation flow. The implementation program therefore extended the shared service/repository paths instead of creating a second web-only data model.

Across PRs #84–#96, the program closed the audited gaps across:

- cross-surface capability contracts and Insights controls;
- food search, saved-food reuse, structured meal logging and editing;
- meal draft creation, review, editing, question answers, confirmation, and cancellation;
- structured recipe creation/editing, recipe actions, planning, groceries, and atomic recipe composition;
- native CSV import preview/commit using the canonical parser and idempotent meal importer;
- historical meal search/details, Insights trends/patterns/provenance, water/weight history and editing;
- account, connection, household, export, billing, and settings surfaces with explicit channel boundaries.

The final PR #96 added the missing website compose workflow and kept recipe persistence, planning, explicit grocery rows, authorization, and idempotency in the canonical atomic service.

## Code, data, and security state

- Railway PostgreSQL is the production system of record; the canonical schema was already current at deployment and `bun run db:migrate` was idempotent.
- The final PR made no migration or environment-variable changes. No secrets were added to the repository.
- Supabase is not an active runtime dependency. `src/no-supabase-runtime.test.ts` and the legacy-auth/runtime invariants are part of the passing architecture suite; historical ADR references are documentation of the retired migration, not active code paths.
- Structured meal guards remain server-side: portions and nutrition totals are derived/validated by canonical services, and recipe compose accepts only explicit grocery rows rather than inferring pantry inventory.
- Ownership, capability, optimistic-version, idempotency, and RLS checks remain in shared service/repository paths.
- No real Stripe charge or production billing mutation was performed.

## Cleanup and remaining risk

No production test data was created in this audit. CI database checks use ephemeral PostgreSQL and synthetic reviewer accounts. The account-deletion, export/privacy, and RLS smoke suites cover cleanup/isolation behavior in that fixture.

The implementation is complete, but two evidence limits remain explicit:

1. The matrix does not claim a live authenticated production browser journey for every website mutation; it claims source/UI coverage, CI database coverage, OAuth browser smoke, and direct production boundary/asset probes.
2. The matrix does not claim a live external MCP client invocation of every safe tool in production. It records MCP registration/schema/structured-output coverage and the canonical service/database tests. A separate connector certification pass could exercise those tools against a dedicated reviewer account if required.

Operationally, the deployment runbook still calls for an isolated backup restore exercise before accepting paid users. That is a launch-readiness task, not an unresolved MCP↔website parity gap.

## Final verdict

**Implemented: yes.** All audited cross-surface outcomes are complete, all 72 registered MCP tools are assigned and covered by documented evidence, and the seven channel-specific exceptions are intentional and encoded. **Unresolved parity gaps: none.**
